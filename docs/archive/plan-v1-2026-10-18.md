## 0. Tóm tắt điều hành

### 0.1 Sản phẩm

**Plugin guardrails dạng proxy OpenAI-compatible** (QĐ-A1, QĐ-A2): chèn giữa client và model, **1 điểm chặn** cho mọi app dùng OpenAI SDK:

```
client (SDK OpenAI / LangChain / curl)
   base_url = http://127.0.0.1:20129/v1        ← proxy (sản phẩm của đồ án)
        ▼
[TRẠM 1 INPUT] → [TRẠM 2 CONTEXT] → forward → [TRẠM 3 OUTPUT] → client
        ▼
   9router 127.0.0.1:20128/v1 (36 model; QĐ-C1, QĐ-C12)
```

3 trạm (input/context/output) × 3 họ phát hiện (F1 luật+Unicode · F2 classifier OSS · F3 LLM judge) × 4 mức can thiệp (block/mask/log/escalate); log **JSONL là nguồn sự thật** + SQLite làm chỉ mục; chạy **Python trực tiếp** trong lúc phát triển (v1), Dockerfile/compose là artefact bàn giao cuối.

### 0.2 Phạm vi v1 (chốt)

- **Làm:** (a) prompt injection **trực tiếp và gián tiếp** ở tầng văn bản (EN + VI, kể cả tầng ký tự: homoglyph/zero-width/tags/mã hoá/biến thể VN); (b) **PII** định danh VN + EN ở cả 3 trạm (mặc định **mask**); (c) đo lường trung thực: ASR, TPR@FPR, over-defense, độ trễ, độ rò, độ bền của judge, độ bền của chính guardrail (fuzz ngưỡng).
- **Hoãn khỏi v1 (không hứa — vá #1):** nhóm `harmful/toxicity` (nháp A §3.2 có `harmful.default: block` nhưng B/C **không có detector nào**) và **egress markdown sanitize** (`egress_md`) — cả hai đưa vào mục "ranh giới" + backlog v2; plan **không** tuyên bố mặc định block nội dung độc hại.
- **Ngoài tầm với của proxy (khai báo, không hứa — mục 1.4):** trạng thái phía server, client gọi thẳng provider, cross-modal, reasoning trace, log/telemetry/kênh phụ, tool thực thi nội bộ app, memory/RAG poisoning.

### 0.4 Kết quả kỳ vọng (đo được; không hứa số trước khi đo)

1. **Δ ASR** giữa C0 (không guardrail) và C3/C4 (guardrail) trên K1+K2, kèm CI + số lần lặp — endpoint chính #1.
2. **FPR hệ trên tập lành** (thường + benign-chứa-từ-khoá) — endpoint chính #2; **GIẢ THUYẾT — không phải khẳng định/kết quả** (chưa có số): ≤5% — mốc đối chiếu Lakera **5,7%** trong Palit (`plugin-architecture.md` §2.2; production 5–15% — `nghien-cuu/N3-*.md`). **Ngưỡng dừng kèm giả thuyết:** nếu FPR hệ **>10%** trên tập benign ở **M3** ⇒ **hạ F2 khỏi vòng can thiệp** (chỉ log) — thi hành theo §6.2 + §7-M3.
3. **Số tự đo đầu tiên** cho VI & tầng ký tự: recall theo từng lớp né tránh + độ trễ CPU thật + TTFT theo `stream_mode` (tài liệu công khai **không có** số TTFT của bất kỳ guardrail streaming nào — `streaming-guardrails.md` §d).
4. **Artefact bàn giao:** proxy chạy được (C0 pass-through + guardrail), bộ test T1–T5, log JSONL có hash-chain + verify, trang log tĩnh, bộ dữ liệu + manifests tái lập, báo cáo theo khung chỉ số mục 6.
5. **Các tuyên bố trần/sàn phải có:** pattern matching có trần **35–45%** trên indirect injection tinh vi và sàn ASR **~15%** — hai con số này là ***mốc tham chiếu ngoài (AgentDojo/InjecAgent), KHÔNG phải trần/sàn của hệ FOX*** (`risk-taxonomy-2026.md` §4.4); mọi defense mất **15–20%** utility (AgentDojo). Recall lớp Unicode **tất định**: **chỉ báo cáo, không đặt mục tiêu** (bộ test do ta tự sinh ⇒ đặt mục tiêu chỉ "tròn" phép đo; T1 đo và công bố kèm bảng "bước nào bắt"); recall **tổ hợp** cũng chỉ báo cáo, không đặt mục tiêu.

### 1.2 Input / output của hệ thống

**Input (mặt API):** request OpenAI-compatible gửi tới proxy —
`POST /v1/chat/completions` `{model, messages[], stream?, stream_options?, tools?, n?, temperature, …}`; và `POST /v1/completions` (legacy — **được kiểm**, mục 2.8); `GET /v1/models` (chuyển tiếp khai báo). Ngoài ra: config `fox-guardrails.yaml`, dữ liệu test, manifest thực nghiệm.

**Output:**
1. Response đã qua 3 trạm: cho qua (allow) · **mask** (thay span PII bằng placeholder) · **block** (JSON error có cấu trúc / deny-frame SSE) · **escalate** (ghi hàng đợi + hành động mặc định an toàn).
2. **Log JSONL** (nguồn sự thật) + SQLite (phiên, escalations) + metrics — schema ở 10.3.
3. Trang log tĩnh (`fox logs report`) + lệnh điều tra `fox logs why --record <id>` (tiêu chí nghiệm thu ở §3.6).
4. **Luồng dữ liệu ra ngoài (khai báo bắt buộc):** khi bật F3, nội dung (đã mask PII) được gửi tới **judge qua 9router — nhà cung cấp thứ ba ⇒ là một luồng xử lý dữ liệu MỚI** (nội dung người dùng rời máy); phải khai báo trong chính sách dữ liệu (§4.5) và có **tuỳ chọn TẮT judge** (`f3.enabled: false` ⇒ chạy như C3) để giữ phương án không gửi dữ liệu ra ngoài.

### 1.3 Ranh giới phạm vi

- **Trong:** văn bản đi qua proxy trên 2 chiều; định danh PII theo định dạng VN+EN; tấn công EN+VI; đo lường; proxy + test + log + báo cáo.
- **Ngoài (không hứa):** harmful/toxicity đầu ra (v1), egress sanitize markdown (v1 — dù EchoLeak là động lực: ghi rõ động lực vẫn tồn tại, chỉ chưa làm), cross-modal, fine-tune model (v2+), app demo RAG đầy đủ (tuỳ chọn — harness tự viết là client chuẩn), UI/UX sản phẩm.
- **Tư thế khoa học:** "đo được + khả thi", không claim "sản phẩm dùng được"; mọi tuyên bố thiếu số phải có nhãn `[cần đo — M0/Mx]`.

## 2. Kiến trúc

### 2.1 Ba trạm và luồng request

```
 client (SDK OpenAI) — base_url = http://127.0.0.1:20129/v1
        │  POST /v1/chat/completions {model, messages[], stream?, tools?, stream_options?}
        ▼
 [0] HTTP layer : schema strict (pydantic), registry phiên (2.8), route, whitelist path
        │
        ▼
 [1] TRẠM 1 — INPUT : chuẩn hoá → F1 → (F2 khi luật chạm) → verdict → action
        │              nhìn: role=user; system nếu policy bật
        ▼
 [2] TRẠM 2 — CONTEXT: quét role=tool, RAG chunk, system, lịch sử assistant
        │              + đánh giá toàn phiên (state, multi-turn) — chỗ indirect injection nằm
        ▼
 [3] FORWARD : HTTPX async → 9router 127.0.0.1:20128/v1 (giữ nguyên model/params/headers)
        │
        ├──── stream=false ─────────────┬──── stream=true ─────────────────────┐
        │  [4] TRẠM 3 — OUTPUT         │  [4'] TRẠM 3 — OUTPUT theo SEGMENT       │
        │  quét CẢ CỤC: text +          │  đệm câu + overlap K=512; tool-call JSON │

```

| # | Bước | Việc cụ thể | Đầu ra |
| --- | --- | --- | --- |
| 0 | HTTP layer | Schema strict; **từ chối có mã** shape lạ (2.8); tính `sid` server-side; route: chat/completions + completions qua trạm, models = passthrough khai báo | `RequestCtx` |
| 1 | TRẠM 1 INPUT | (a) chuẩn hoá Unicode (13 bước, §3.2); (b) **F1 luật chạy trước** (rẻ, tất định); (c) điểm vùng nghi ngờ → F2; (d) mơ hồ + có ngân sách → F3 **async** (2.6); (e) gộp verdict (§3.5) | `Verdict(station=input)` |
| 2 | TRẠM 2 CONTEXT | Quét mọi nội dung **không do người dùng gõ lượt này**: tool output, RAG chunk, system, lịch sử assistant; + scoring toàn phiên (peak+accumulation) | `Verdict(station=context)` |

**Phân biệt `egress_md` — tránh hiểu sai phạm vi (vá lượt 3):** trạm 3 **quét nội dung markdown NHƯ TEXT** — điều này **TRONG v1** (bắt chỉ thị ẩn trong markdown: comment HTML, link/title, alt-text…); thứ **đã hoãn khỏi v1** chỉ là **sanitize egress URL/ảnh** (chặn URL/auto-fetch do model sinh — lớp EchoLeak, §1.1#6; QĐ Q6). EchoLeak là nguồn gốc đề tài ⇒ nếu không tách 2 câu này, pain-point #6 bị đọc sai là "ngoài phạm vi". **Câu chốt: quét markdown như text = v1; sanitize egress URL/ảnh = v2 (đã hoãn).**

**Vì sao 3 trạm:** trạm 2 là nơi indirect injection nằm (số 70%/8% ở §1.1#1) và là trạm "kiểm được ngữ cảnh đã nhét vào `messages`" — **không** kiểm được kho dữ liệu (khai báo §1.4); trạm 3 là chốt cuối cho PII rò qua câu trả lời (OWASP: phát hiện ở output *"is a last line and it is porous"* — `risk-taxonomy-2026.md` §LLM02, dẫn qua bài test-guide `[THỨ CẤP]`). Thị trường ủng hộ thiết kế nhiều trạm theo "trust boundary" thay vì quét mọi chunk (AWS/baristalabs 23/07/2026 — `streaming-guardrails.md` §e.1).

### 2.2 Streaming: mode `sentence` + overlap K=512 (mặc định)

Hai yêu cầu kéo ngược nhau: *"A guardrail wants to accumulate text before judging. Streaming wants to release text before judging."* (`streaming-guardrails.md` §a). **Chọn `stream_mode: sentence`** làm mặc định; 3 chế độ cấu hình được: `hold` (đệm toàn bộ — chính xác nhất, mất streaming), `window` (cửa sổ trượt — nhanh nhất), `pass` (chuyển thô + log — **chỉ** để đo baseline C0/C5). Có thể đổi mặc định **chỉ sau khi M0 đo TTFT** (§7).

Đặc tả đệm (đủ để code):

1. **Phân đoạn câu**: cắt tại `.`, `!`, `?`, `\n\n`, `。？！`; tôn trọng số thập phân `1.234` và viết tắt VN (`vd.`, `etc.`) — ranh giới câu là điều kiện dừng chuẩn hoá (SentGuard: `τ_i = inf{ t>τ_{i−1} : b(y≤t)=1 }`).
2. **Đệm phát**: giữ **câu hiện tại chưa phát + đuôi overlap K=512 ký tự** của câu trước (`K` cấu hình được). **K=512 là sàn, không phải tuỳ chọn trang trí**: cửa sổ 512 ký tự bắt **96/128** cặp, quét trong nội bộ chunk chỉ **38/128** (`streaming-guardrails.md` §c.1, arXiv 2608.10279 **`[preprint]` — phải đo lại trên phân phối VI của đồ án ở M0**). Lưu ý: entity dài (địa chỉ) có thể **bị `max_segment_chars` cắt khi flush** — xem mục 6(d) dưới.
3. **Trigger kiểm** (cái nào trước): (a) hết câu; (b) đệm ≥ `max_segment_chars=600` (chặn câu "bất tử"); (c) quá `max_hold_ms=1500` kể từ lần phát trước → phát phần chắc chắn an toàn tới **ranh giới từ an toàn gần nhất**, giữ đuôi lại.
4. **Không bao giờ rescan toàn prefix** — chi phí quadratic: chunk 512 ký tự → **13.261 ms**; chunk 8 ký tự → **829.640 ms** (~62×; response 16.384 ký tự) (`streaming-guardrails.md` §c.1/D5/D6). Chỉ quét `(đuôi overlap + segment mới)` + máy trạng thái "mẫu dở".
5. **Ngân sách gọi detector**: F1 luật chạy mọi segment; F2/F3 theo lịch **"1 lần/đầu response + 1 lần/mỗi 5 segment"** — đối chiếu: Bedrock quét mỗi 50 ký tự tốn **100 lần đánh giá** cho 5.000 ký tự; batch 1.000 ký tự còn **5 lần** (**giảm 20×**) (`streaming-guardrails.md` §c.3/D9).
6. **PII bị cắt qua nhiều chunk** — 3 lớp + 1 tổng quát hoá (vá R5):
   - (a) overlap `K=512` bao mọi entity ≤512 ký tự (thẻ 16–19 số, CCCD 12, IBAN — `vietnamese-pii-formats.md` Phần A);
   - (b) máy trạng thái "mẫu dở": đuôi kết thúc giữa run `[0-9+\-.\s]{8,}` hoặc giữa `local@dom…` ⇒ **không phát** tới khi có ký tự kết thúc;
   - (c) `hold` khi policy `pii_critical` (chốt chặn cuối cho phiên nhạy cảm);
   - (d) **tổng quát hoá "mẫu dở" thành prefix-trie cho MỌI recognizer** (không chỉ số/email): không phát phần đuôi khớp tiền tố của mẫu dở — entity có chữ (`[A-Z]{2}\d{13}` BHYT, hộ chiếu `[A-Z]\d{7}`, biển số `51A-123.45`, địa chỉ dài) bị flush tại `max_segment_chars` vẫn có thể cắt; phơi nhiễm công bố **theo lớp PII**, không một số chung.

### 2.3 Sự thật không thể tránh: token đã phát thì KHÔNG rút lại được

Đã kiểm chứng chéo 5–6 nguồn (`streaming-guardrails.md` §c.2): SentGuard limitations *"content already released before a later unsafe decision cannot be withdrawn"*; NeMo `stream_first: True` = *"the user has already received the tokens"*; TrueFoundry *"it cannot retract content already shown or acted on"*; comment code TanStack *"can only append to what the consumer saw, never retract it"*. **Retract chỉ tồn tại ở tầng UI** — tác giả tự nói *"a real improvement even though it isn't a fix"* ⇒ **không dùng trong thiết kế**; ghi vào báo cáo như giới hạn.

Hệ quả thiết kế: (i) ngăn phơi nhiễm ở **tầng đệm** (span nguy hiểm không ra khỏi buffer trước khi có verdict); (ii) khai báo `buffered_output: true` cho `sentence`/`hold`; `residual_exposure ≈ 1 segment + K` cho `window`; **full** cho `pass` — kèm câu tuyên bố theo draft spec `agent-hooks` (§12.1a — **draft spec**, repo gốc `responsibleai/agent-hooks`, refreshed 2026-07-15; mirror `github.itlym.cn` bỏ khi trích).

Khi phát hiện giữa dòng, đúng **3 hành vi** (phân biệt mức "rút lại"):

| Hành vi | Mô tả | Mặc định của ta |
| --- | --- | --- |
| **Sever + deny frame** | Cắt stream: 1 chunk SSE cuối + `finish_reason`, mọi token sau không phát; body "provider-compatible" để SDK render như refusal bình thường | Documented cho **injection high-severity đã đủ căn cứ** (F1 tất định / quorum) |
| **Redact tại chỗ** | `flushBuffer()` → `redactContent(...)` — chỉ áp cho phần **còn trong buffer**; thay span bằng placeholder rồi phát tiếp | Documented cho **PII mức mask** |
| **Retract** | Không tồn tại ở tầng protocol | **Không dùng** (như trên) |

**Tách 2 loại frame kết stream (vá M7) — schema chốt:**

| Loại | Khi nào | Trường bắt buộc (SSE `data:` JSON) | Được/kết thúc |
| --- | --- | --- | --- |
| **(a) Vi phạm nội dung** | injection đủ căn cứ (F1 tất định / quorum) ⇒ `sever+deny` | `id` · `object:"chat.completion.chunk"` · `created` · `model` · `choices[0].delta.content` (câu refusal) · `choices[0].finish_reason` = hằng số lớp vi phạm (`content_filter`) | 1 chunk cuối + `data: [DONE]`; **không** có trường `error`; không phát token sau |
| **(b) Lỗi hạ tầng** | detector/breaker chết, timeout, upstream đứt giữa stream | `error.type` (lớp lỗi) · `error.code` (`guard_unavailable`) · `error.message` | đóng stream ngay; **không** `choices` giả, **không** `finish_reason` |

- **Chunk `usage` (khi `stream_options.include_usage=true`):** chỉ tồn tại **1 lần, ở cuối** stream. Nếu upstream đã phát usage trước khi deny ⇒ **forward nguyên trạng** (không sinh lại). Nếu deny chặn trước khi usage về ⇒ **không tự sinh** chunk usage (trường `usage` là optional với SDK; tránh số giả) — ghi `usage_emitted:false` vào log; test byte-compat bằng SDK thật ở M4 (cả 2 loại frame).
- Phân biệt (a)/(b) cần cho byte-compat **và** cho cách đo "ký tự phơi nhiễm trước deny".

**Chốt byte-compat khi mask giữa dòng — "không gửi lại":** SSE là append-only — delta đã phát **không** sửa/gửi lại được (gửi lại một đoạn đã phát = nhân đôi nội dung trên UI). Vậy mask **chỉ áp cho phần còn trong buffer + mọi token chưa phát**; phần đã phát tính là `exposure_chars` (công bố theo lớp PII, không một số chung). **Ảnh hưởng UX:** người dùng có thể đã thấy **phần đầu của entity** (vd 9/12 chữ số CCCD) trước khi placeholder thay phần còn lại ⇒ phơi nhiễm một phần; giảm bằng (a) K=512 + mẫu-dở trie (§2.2 mục 6) chặn phát giữa entity; (b) `hold` cho phiên `pii_critical`; (c) cửa sổ đệm ≥ entity dài nhất đã khai báo. Không hứa "che kín" — đo và công bố.

### 2.4 CHỐT — Mặc định can thiệp (một nghĩa duy nhất, áp cho log/manifest/policy)

> **Nguyên tắc chốt:** *PII ⇒ mask ở mọi trạm. Injection ⇒ **chỉ luật tất định được block một mình**; classifier/judge chỉ góp phiếu và **block cần quorum ≥2 họ độc lập**. Không có mặc định `block` nào khác trong v1.*

| Trạm | Injection (deterministic) | Injection (không tất định) | PII | Ngoài phạm vi v1 |
| --- | --- | --- | --- | --- |
| **1 INPUT** | **block** (kèm log lý do) | phiếu; **block khi quorum ≥2 họ ≥ MEDIUM**; còn lại log/escalate | **mask** trước khi gửi model | — |
| **2 CONTEXT** | **block/locate**: cách ly span độc (placeholder + bọc "untrusted content") khi tất định | phiếu; quorum như trạm 1; escalate khi lặp ≥3 lần/phiên | **mask** | — |
| **3 OUTPUT** | **sever+deny** (stream) / chặn cục (JSON) | phiếu; quorum | **mask** (redact trong buffer) | harmful/toxicity & egress markdown = **HOÃN, không hứa** |

- **Vì sao mask là mặc định PII, không block:** mask là mức duy nhất giữ utility (PII xuất hiện trong yêu cầu hợp lệ: địa chỉ giao hàng, tra cứu đơn hàng); chặn ở input bằng mask là biện pháp "sớm" nhất (OWASP khuyến nghị uỷ quyền trước khi truy hồi; Bedrock cấu hình `ANONYMIZE`).
- **Vì sao không block theo classifier đơn lẻ:** over-defense **40,1%** (PG2) ⇒ block méo vận hành; block chỉ khi **luật tất định** hoặc **quorum quy định ở §3.5**. Quyền veto của **khối PII tất định (checksum/allowlist) là veto cho mức MASK** (buộc mask dù F2 im lặng) — **không** phải veto block (chốt M2: tách "checksum ⇒ F1 veto" khỏi "ML/NER ⇒ F2 phiếu").
- **Escalate** = severity HIGH nhưng dưới ngưỡng block, hoặc ≥3 lần chạm cùng phiên → **hàng đợi async + hành động mặc định an toàn theo timeout**; ngân sách: escalate chỉ cho HIGH/tín hiệu đặc biệt (FPR guardrail tham chiếu **5,7%** ⇒ escalate mọi "medium" = ~57 ca/1k request — không khả thi cho một người trực; `plugin-architecture.md` §2.2).
- **Hành vi `escalate` trả về client (chốt):** `escalate` **không phải một hành vi mạng riêng** — không có "escalate frame"; client chỉ thấy allow/mask/block đúng theo mức ở bảng trên, còn escalate chỉ ghi **hàng đợi async** (+ `escalate_id` trong record) cho analyst. Giữ **hành động mặc định an toàn theo mức**: PII ⇒ **mask**; injection đã đủ căn cứ ở trạm 3 ⇒ **sever+deny / block theo trạm**; injection chưa đủ căn cứ (trạm 1/2) ⇒ **allow + log + cờ phiên** (đúng triết lý "không block theo classifier đơn lẻ" — không chặn oan, siết phiên cho lượt sau qua `escalate_after_hits`). Người trực điều tra **sau**, không nằm trong đường nóng.
- **Escalate không hứa "người trực 24/7"** và **không hứa năng lực 72 giờ** (Điều 29 NĐ 356/2025): phát biểu đúng = *"log đủ chi tiết (timestamp, chủ thể, loại dữ liệu, bằng chứng) để một tổ chức có thể thực hiện nghĩa vụ"* (vá P3).
- **on_low_conf (vá R15):** entity rủi ro cao (CCCD, thẻ, số tài khoản) **không bao giờ log-only** — mask trước, khôi phục sau theo yêu cầu; entity khác: log.

### 2.5 Đệm tool-call & vòng đời segment (chi tiết code)

- Delta `tool_calls[].function.arguments` được **đệm riêng** tới khi JSON hoàn chỉnh rồi mới quét và phát — tránh đúng lỗi APISIX tự thừa nhận (*"tool-call arguments themselves are not sent to Lakera"*).
- Verdict theo segment: `allow` (phát) · `redact` (phát bản đã mask) · `sever` (dừng, deny frame) được tính từ findings của segment + state phiên.
- Kiểm byte-compat bằng **SDK thật** (Python/JS/LangChain), không chỉ curl: `[DONE]`, `include_usage` không mất (QĐ-C10), frame deny parse được như refusal.

### 2.6 Ngân sách độc lập: đường nhanh (p95) ≠ trần timeout (vá #2)

Hai khái niệm **tách hẳn** (trước đây bị trộn — B/C nói "<100 ms input, <150 ms output" trong khi A đặt timeout F2 150 ms / F3 1.500 ms):

| Khái niệm | Định nghĩa | Số hiện có | Trạng thái |
| --- | --- | --- | --- |
| **Ngân sách đường nhanh** (hot path) | p50/p95 **độ trễ THÊM** của F1 + (F2 khi luật chạm) trên một segment, đo trên CPU máy này | Mốc tham chiếu ban đầu: <100 ms input / <150 ms output — **là mốc, không phải cam kết** | `[cần đo — M0]`; chốt sau khi có bảng p50/p95 thật |
| **Trần timeout** (hard) | Thời gian tối đa 1 detector được chạy trước khi bị cắt (breaker) | F1 **20 ms** · F2 **150 ms** · F3 **1.500 ms** | Giữ; nhưng F2 150 ms có thể **phải nới** nếu M0 cho thấy PG2-86M CPU chậm hơn nhiều (92,4 ms/512 tok **trên A100** — `risk-taxonomy-2026.md` §4.2) |
| **F3 tư thế** | **Async, ngoài hot path**: verdict của judge áp cho *lượt/segment sau* hoặc cho phân tích offline; response hiện tại không chờ judge | Judge chỉ chạy trong dải mơ hồ (0,3 ≤ score < 0,8) + theo lịch segment | Chốt — tránh cộng dồn >1,5–2 s/lượt (gateway floor ~430 ms — `jev-model.md` §3.7) |

**Quy tắc ngữ nghĩa F3 async (chốt — vá lượt 3, xoá chỗ chặn viết verdict-merge):** kết quả F3 của lượt `t` đến muộn **CHỈ** được dùng để (i) **ghi log** (record judge gắn `applies_to: "t+1"`), (ii) **cập nhật cờ phiên** (state/accumulation — §3.4), (iii) **được nâng mức tối đa 1 bậc khi gộp quorum cho lượt `t+1`** (§3.5). **KHÔNG hồi tố** hành động của lượt đã trả — response đã phát/đã gửi không bị sửa, không bị chặn lại sau. **Ghi chú đối lập:** muốn F3 tham gia quyết định *trong lượt* thì phải **chấp nhận độ trễ** (chờ judge trước khi trả / `hold` buffer) — tức **đảo ngược vá #2** (F3 async ngoài hot path); nếu làm, khai báo như một **arm phụ** và đo độ trễ tăng thêm, không trộn vào C4/C5 mặc định.

**Ghi rõ trong plan:** các số ngân sách **phải đo ở M0 trước khi cam kết**; nếu F2 CPU vượt p95 mục tiêu → phương án đã định trước: (a) ONNX + quantization + model nhỏ (`plugin-architecture.md` §1.A); (b) F2 chỉ chạy trên segment "chạm luật" + lịch thưa hơn — cả hai đều có sẵn trong tài liệu nghiên cứu.

### 2.7 Fail-mode theo trạm (+ chống treo, + chống oracle)

| Trạm | Fail-mode mặc định | Lý do | Đối chiếu thị trường (ta chọn KHÁC) |
| --- | --- | --- | --- |
| 1 INPUT | **fail-closed** (lỗi có cấu trúc, không gửi model) | Điểm sớm nhất, rẻ nhất; thử lại được | Portkey `Deny FALSE` (request vẫn gửi, HTTP 246); Cloudflare: lỗi ⇒ *"request will proceed without evaluation"*; APISIX `fail_open: true` |
| 2 CONTEXT | **fail-open + log** (nhánh luật tất định đã match thì fail-closed) | Cách ly sai 1 chunk RAG phá câu trả lời đúng (utility 15–20%); trạm 3 còn chốt cuối | Cùng nhóm trên |
| 3 OUTPUT (non-stream) | **fail-closed** | Response sinh xong — chặn/mask không "phí" gì | NeMo `stream_first: False` style |
| 3 OUTPUT (stream) | **fail-buffered**: dừng phát tiếp, chuyển đệm; không kịp quét ⇒ kết stream bằng frame lỗi | Theo draft spec `agent-hooks`: *buffer until combined verdict permits (MUST) hoặc khai `buffered_output:false`* | APISIX mặc định `fail_open: false` = buffer |

- **Chống treo (bắt buộc, vì fail-closed là vũ khí DoS):** timeout cứng mỗi detector + **circuit breaker** (fail liên tiếp N lần ⇒ tắt T giây, đếm trong metrics); nối **cap đầu vào B13 ↔ cap log/queue**; có soak test ở M6 (vá M3).
- **Chống oracle (vá R16):** phía client chỉ thấy **2 lớp mã** (violation / guard-unavailable) — mọi chi tiết (rule_id, score, ngưỡng, họ đồng thuận) **chỉ trong log**; đo jitter độ trễ; thêm ô fuzz ngưỡng (~50 request biến thiên quanh ngưỡng) vào M6. Đây là bề mặt oracle **có chủ đích tối thiểu** — cần 2 lớp mã để phân biệt "chặn do vi phạm" vs "chặn do sự cố"; chi tiết hơn là không an toàn.

### 3.0 Hợp đồng interface — pseudo-signature (đặc tả; **KHÔNG** phải code thật)

```text
Detector (mọi họ F1/F2/F3 dùng chung một hợp đồng):
  nhận: ReadView { text            # segment (stream) hoặc full text (non-stream)
                   view            # raw | no_invisible | nfkc | skeleton | vn_nodiac | decoded[i]
                   offset_map      # view → raw
                   metadata { station, role, lang, case_id, turn_idx, session_sid, policy } }
  trả:  Finding[]

Finding:
  detector_id · family(F1|F2|F3) · kind(injection|pii) · label · score ∈ [0,1]
  spans[] { start, end }           # TOẠ ĐỘ THEO view_used — detector KHÔNG tự đổi
  latency_ms · rule_id · view_used · severity (theo §3.5) · evidence_preview · span_hash_hmac

Verdict (kết xuất của tầng gộp §3.5 — không phải của detector):
  severity_max · quorum_families[] · rule_id · thresholds_version · action ∈ {allow, mask, block, escalate, log}
```

- **Trách nhiệm offset (chốt):** detector trả span **theo `view_used`** (khai báo bắt buộc); tầng pipeline (B11) compose `offset_map(view→raw)`; **mọi consumer (mask/log/deny) chỉ nhận span đã quy về text gốc (raw)** — điều kiện để mask không lệch vị trí (B0, §3.2).
- Finding thiếu `view_used` hoặc span không map được về raw ⇒ **REJECT** (lỗi lập trình — có test trong CI).
- **Gọi:** F1/F2 chạy trên **segment** (stream, kèm đuôi overlap K=512) hoặc **full text** (non-stream); F3 **async** ngoài hot path — cùng chữ ký, nhưng verdict áp cho segment/lượt sau (§2.6).

### 3.4 Máy trạng thái phiên (đa lượt)

- **Đếm theo phiên** (registry §2.8): số lần chạm, verdict gần nhất, cờ crescendo; **peak + accumulation** (ρ=0,45; βe; βr; τ=0,7 theo công thức nghiên cứu) — số tham chiếu: recall **90,8% @ FPR 1,20%** trên 10.654 hội thoại (WildJailbreak/WildChat — `multiturn-attacks-part2.md` §2.3, `[preprint]` 2602.11247) — **phải đo lại trên phân phối của đồ án**.
- **Judge theo-phiên không đáng tin**: sụp **26/26 → 14/26 (−46 pp)** dưới adaptive rewrite (`multiturn-attacks-part2.md` §2.1) ⇒ chỉ dùng làm lớp phụ.
- **Cố định ngân sách thử**: ≤10 lượt/phiên, ≤3 retry/lượt, **không restart** (MT-JailBench limited setting) — nói rõ đây là **trần nhân tạo**, không phải "đã chống tấn công thích nghi" (vá W12).
- Tool descriptor **thay đổi giữa phiên** → log + escalate tín hiệu.

### 3.5 Gộp quyết định (quorum — KHÔNG `any(flagged)`)

**Vì sao không OR:** 5 guard × accuracy 90% ⇒ ~**41%** xác suất có ≥1 chặn oan (`nghien-cuu/N3-*.md`); Lakera FPR **54,9%** trong BELLS-O; thêm lớp = thêm FP **lẫn** độ trễ (NVIDIA: lớp 1 +~0,5 s, 75%→83%; thêm nữa ~99%; throughput **112,9→98,7 tok/s** — `plugin-architecture.md` §2.2).

```
for f in findings:
    if f.family == rules and f.deterministic:   sev[f] = HIGH      # checksum/allowlist/Unicode hit
    elif f.family == rules:                     sev[f] = MEDIUM if f.hit else LOW
    elif f.family == classifier:                sev[f] = HIGH nếu score ≥ θ_high VÀ có F1 hỗ trợ,
                                                         MEDIUM nếu ≥ θ_low, còn lại LOW
    else:  # judge — F3
        sev[f] ≤ MEDIUM; không bao giờ block; dịch chuyển tối đa 1 bậc khi đồng thuận

block    ⟸  (tồn tại F1 deterministic hit)  OR  (số HỌ ĐỘC LẬP có sev ≥ MEDIUM ≥ 2)
escalate ⟸  sev_max == HIGH and not block
mask     ⟸  kind == pii và sev ≥ MEDIUM (hoặc F1 PII deterministic — veto mask)
log      ⟸  còn lại
# mọi nhánh gắn rule_id + thresholds_version + quorum[] để log giải thích được
```

**Bảng tra gộp verdict `(F1, F2, F3) → severity → action` (thay mô tả chữ — tra trực tiếp; hàng có `kind == pii` đọc cột action là **mask**):**

| F1 (luật+Unicode) | F2 (classifier) | F3 (judge — async) | severity tổng | action (injection) |
| --- | --- | --- | --- | --- |
| **hit tất định** (checksum/allowlist/Unicode) | bất kỳ | bất kỳ | **HIGH** (veto F1) | **block** (output stream: sever+deny; input/context: block/cách ly span) |
| hit ngữ nghĩa (MEDIUM) | **≥ θ_high** (⇒ HIGH nhờ F1 hỗ trợ) | bất kỳ | **HIGH** | **block** (quorum 2 họ ≥MEDIUM: F1↔F2) |
| miss | **≥ θ_high** nhưng **không** F1 hỗ trợ | < θ_low / chưa về | **MEDIUM** | log (+ escalate nếu ≥3 chạm/phiên) |
| miss | **∈ [θ_low, θ_high)** | < θ_low / chưa về | **MEDIUM** | log |
| miss | **≥ θ_low** | **≥ θ_low** (đồng thuận; verdict đã về) | **MEDIUM ×2 họ** | **block** (quorum F2↔F3); nếu F3 **chưa về** (async) ⇒ log + escalate, quorum áp ở segment/lượt sau — **không hồi tố lượt đã trả** (quy tắc §2.6-F3) |
| miss | < θ_low | **≥ θ_low** (đơn độc; tối đa dịch 1 bậc khi đồng thuận) | ≤ MEDIUM | log — F3 **không bao giờ block** một mình |
| miss | miss | miss | LOW | log |

> Tổ hợp không liệt kê ⇒ áp **công thức tổng quát** trong pseudo-code trên: `block ⟸ F1 tất định OR quorum ≥2 họ ≥MEDIUM; escalate ⟸ sev_max=HIGH & not block; mask ⟸ kind=pii & sev≥MEDIUM (hoặc F1 PII veto); log ⟸ còn lại`. θ theo từng họ: bảng ngay dưới.

**Bảng ngưỡng (placeholder — hiệu chuẩn lại trên dev set của đồ án; quy tắc M4: F2 đơn độc tối đa MEDIUM để hàng đợi escalate không phình):**

| Detector | θ_low | θ_high | Quyền |
| --- | --- | --- | --- |
| F1 tất định (checksum/allowlist/Unicode) | — | hit=HIGH | **Veto block** (injection); **veto mask** (PII) |
| F1 ngữ nghĩa nhẹ (regex không checksum, context) | có/không | — | Phiếu MEDIUM |
| F2 PG2 86M · deberta-v3-v2 | **0,30** | **0,80** | Phiếu ≤HIGH (HIGH chỉ khi có F1 hỗ trợ) |
| F2 PII recognizer VN | theo entity | entity checksum = HIGH | **mask**; không veto block |
| F3 LLM judge | **0,30** (mở dải defer) | **0,80** | Phiếu, không block — **async** |

### 3.6 Audit trail (giải thích được từ record, không cần text gốc)

Mỗi quyết định = 1 record JSONL (schema đầy đủ ở **10.3**) với các nhóm: định danh (`record_id`, `ts_utc`, `session_id`, `subject_key`, `station`, `direction`, `model`) · đầu vào (`raw_sha256`, `raw_len`, `views_used[]`, `decoded_layers`) · **biến đổi đã áp** (`transforms[]` theo thứ tự: `{step:"B3", removed:3, cps:[...]}`, `{step:"B10", kind:"base64", bytes:64, preview_sha256}`) · phát hiện (`findings[]` với `span` quy về raw + `score` + `severity` + `evidence`) · quyết định (`action`, `rule_id`, `quorum[]`, `thresholds_version`, `config_hash`) · vận hành (`fail_mode_used`, `latency_total_ms`, `breaker_state`, `escalation_queue_id`, `retry_count`, `http_status`).

**Tiêu chí nghiệm thu (test được, vào CI):** `fox logs why --record <id>` in ra lý do chặn **chỉ từ record** (không cần text gốc). Không đạt → coi như chưa có audit trail.

**Bảo vệ log (vá #5)** — chi tiết ở §4.5: hash-chain toàn vẹn · test "raw không rò ngoài store" · viewer escape/CSP · **`span_hash` = HMAC + salt per-deployment** (không hash trần — SĐT sau khi biết đầu số còn ~10⁷; CCCD biết tỉnh+năm sinh còn vài nghìn ⇒ hash trần là oracle từ điển).

### 4.3 Chia train/dev/test chống trùng lặp

Quy tắc gốc (`datasets-quality.md` §4): *"không bao giờ chia train/test từ hai bộ khác nhau khi chưa dedupe; mọi con số tổng mẫu phải ghi rõ sau dedupe hay theo card"*. Quy trình 5 bước (chạy thật, ghi log):

1. **Dedupe exact + near-dup**: chuẩn hoá (NFKC + lowercase + gộp whitespace) → hash exact; MinHash/Jaccard ≥0,8 near-dup. Ghi tỉ lệ trùng từng cặp nguồn (bảng chồng lấn 11 dòng của `datasets-quality.md` §4 là checklist bắt buộc).
2. **Provenance tag** từng mẫu: `source_id`, `parent_set`, `template_id`. Tập "cha" (JGB ⊃ JBB+JailbreakHub+MultiJail+SafeMTData) **không** tính là nguồn độc lập.
3. **Split theo group** = (`source_id` × họ kỹ thuật × `template_id`); phiên đa lượt cắt **nguyên phiên**; không để cùng template ở cả dev và test.
4. **Tỉ lệ:** dev **20%** (hiệu chuẩn θ, chọn FPR mục tiêu, tuning ρ/β) · test **80%** (held-out, khoá sau khi chốt ngưỡng, mở đúng 1 lần). **Train chỉ tồn tại nếu fine-tune detector** (ngoài MVP).
5. **Chống nhiễm bẩn:** chạy chéo trên bộ detector **chưa từng thấy** — bài học "Passing the Test You Trained On": PIGuard đứng đầu BIPIA **95,1% @1%FPR** nhưng chỉ bắt **2,1%** injection AgentDojo; Kendall τ = **0,01** (`nghien-cuu/N4-*.md` §3). Điểm test cao bất thường ⇒ kiểm tra ngay bộ đó có trong data train của detector không.

**Ánh xạ ô:** K1 test = 100 JBB harmful + 100 VI (rikka-snow lọc + dịch); dev = deepset+gandalf (chỉ smoke/hiệu chuẩn — quá nhỏ/thiên lệch để làm số chính). ## 5. Thực nghiệm

### 5.1 Câu hỏi thực nghiệm RQ1–RQ5

> **Khoá trước khi chạy** (vá W1/W3): mọi tuyên bố ASR ghi rõ định nghĩa **targeted/untargeted**, `k` lần thử, nhiệt độ, judge; `k=1` overstate **12–24 điểm %**, temp 0→1 phồng tới **54 điểm %** (`papers-pii-and-eval.md` §(ii)); **mọi ΔASR dưới ~10 điểm % không được tuyên bố** nếu judge chưa qua kiểm chứng.

**RQ1 — Hiệu quả theo họ detector (tấn công một lượt).** *Bật guardrails (C1/C2/C3/C4) giảm ASR trên tấn công một lượt bao nhiêu so với C0, cùng model, cùng bộ ca?* Đo: ASR từng arm + TPR@1%FPR từng detector; so chênh lệch kèm CI. Dự đoán có cơ sở: C2/C3 mạnh nhất trên EN in-distribution (recall@1%FPR 97,5% công bố) nhưng **vẫn còn phần vượt** (0,0207; LODO 0,757; trần 38,8% — `risk-taxonomy-2026.md` §4.4); C4 không cộng tuyến tính (thêm lớp tăng bắt nhưng tăng FP/độ trễ — NVIDIA 75→83→99%, throughput 112,9→98,7).

**RQ2 — Khoảng cách ngôn ngữ VI vs EN.** *Cùng cấu hình, ASR_vi có cao hơn ASR_en không, họ nào lệch nhất?* Đo Δ kèm CI; recall F2/F3 trên VI ở **cùng FPR**; FPR của F1 trên VI lành; recall/precision PII entity-level VI vs EN. Dự đoán: dịch sang ngôn ngữ ít nguồn lực nâng ASR **<1% → 79%** (GPT-4); LlamaGuard −9%/−18% DSR trên ĐNÁ (`vietnamese-evasion-and-law.md` §B) — mọi số VI là **giả thuyết cần đo**, không trích như số đã biết.

**RQ3 — Đa lượt: scoring cấp phiên có cần thiết?** *Per-turn + scoring phiên (peak+accumulation, proxy-level, không cần LLM) bắt được bao nhiêu % chuỗi đa lượt @FPR mục tiêu, nhanh hơn per-turn thuần bao nhiêu lượt?* Đo: recall phiên @FPR≤1% (hiệu chuẩn trên benign sessions), **detection latency = lượt đầu bị chặn**; ASR live (block bật giữa phiên, ngân sách ≤10 lượt/≤3 retry, không restart). Biến thể: per-turn thuần · +session scoring · judge-đọc-cả-phiên (đối chứng âm — sụp −46pp dưới rewrite).

**RQ4 — Biến thể né tránh (tầng ký tự + tiếng Việt).** *Pipeline B1–B13 bắt được bao nhiêu % ca đơn lớp và ca tổ hợp?* Đo: recall từng lớp (homoglyph · zero-width · tags · base64/hex/ROT13 · fullwidth · NFC/NFD · mất dấu · teencode · chèn dấu cách) + tổ hợp A9; tỉ lệ "bắt được nhờ đúng 1 phép chuẩn hoá"; FPR trên VI lành. Dự đoán: đơn lớp phần lớn bắt được (kỳ vọng định tính — **chỉ báo cáo, không đặt mục tiêu %**: bộ test tự sinh, con số % sẽ "tròn" phép đo); tổ hợp là chỗ rơi.

**RQ5 — Cái giá và độ vững của số liệu.** *Guardrail tốn thêm gì (FPR, utility, độ trễ p50/p95, quota), và số ASR có đứng vững dưới chạy lặp + kiểm chứng judge?* Đo: FPR từng detector & hệ (thường + benign-chứa-từ-khoá); escalation/1k request; Δutility/retention/refusal; độ trễ thêm p50/p95 từng trạm (CPU) + TTFT theo `stream_mode`; số call detector/response; judge agreement + variance ≥5 lần.

### 5.3 Định nghĩa "ô quyết định" + thiết kế lặp N=20/cell

- **Ô quyết định** (nơi plan phải kết luận được — vá W4): so sánh **C0 vs C3 vs C4 trên K1 và K2**. Power analysis: **MDD ≈ 18,2 điểm % ở n=100** (`nghien-cuu/N4-*.md` §4, arXiv 2609.25173 `[preprint]`); hai defense lệch thật 5 điểm % bị xếp sai thứ tự **~21%** nếu chạy 1 lần ⇒ **chốt: ô quyết định chạy lặp N=20 lần/cell** (mẫu "Adaptive Adversaries", arXiv 2607.18063: N=5/cell cho khác biệt lớn, **replicate N=20/cell cho so sánh then chốt**).
- **Cách hiện thực hoá trong ngân sách:** mỗi cell = một **bộ ca rút gọn đã khoá** — K1r = 50 EN + 50 VI = **100 call**; K2r = 10 phiên × 8 = **80 call**; mỗi vòng lặp = 1 lần chạy độc lập (seed khác) trên bộ rút gọn; 3 arm × 2 cell × 20 vòng = **10.800 call** (khoản lớn nhất của ngân sách — xem 5.4).
- **Hạ cấp có kê khai:** nếu probe M0 cho thấy ngân sách ngày không đủ, hạ N=20 → **N=10 → N=5**, mỗi lần hạ ghi rõ trong báo cáo ("hạ cấp độ chặt") — **không** đổi kết luận âm thầm. Ô **không đủ power** (K2-VI 25 phiên; K4 100 ca; K2-AD 30 phiên) phải liệt kê trước là *"chỉ báo cáo, không kết luận"*.

| `tools` / `tool_choice` | nhận bình thường; tool schema đổi giữa phiên → log + cờ drift (§3.4) |

**Nguyên tắc tái lập:** mỗi run = `run_id` + bản copy manifest + hash của: config YAML · git commit harness · dataset (file hash / revision HF) · prompt judge. Victim temp 0, judge temp 0, seed lưu; **vẫn lưu raw output (đã mask)** để **re-judge offline** khi đổi judge.

### 5.6 Rate limit & canary (kế hoạch B khi model free đổi)

1. **Probe trước (M0):** 100 request liên tiếp lên 1 model phụ → ghi status/429/`Retry-After` → `logs/m0/ratelimit_probe.json`; probe riêng **2 luồng song song** (K2-AD cần attacker+victim đồng thời — áp lực ×2).
2. **Client-side token-bucket + hàng đợi bền:** checkpoint theo `case_id` (resume sau crash); backoff exponential + jitter; cap retry ≤3/lượt; **429 = missing, không phải fail** — loại khỏi mẫu số, **báo missing rate từng ô**; ca missing **chạy bù có ngân sách** tách riêng (không nằm trong "+10%").
3. **Pin model cho ma trận; xoay chỉ cho judge/call phụ trợ** — mọi lần xoay ghi `model_served`.
4. **Canary phát hiện đổi hành vi:** 20 ca cố định/ngày trên **cả model chính lẫn dự phòng**, so với baseline cùng ngày; ngưỡng cảnh báo đề xuất **Δ>5 điểm %** (chốt trước khi chạy); vượt ngưỡng ⇒ chạy lại baseline, báo cáo **ASR tương đối theo baseline cùng ngày** — **không so số tuyệt đối giữa các tuần** (W6/không so được khi model đổi sau lưng router).
5. **Phương án B (T16):** nếu pool free ngừng phục vụ giữa ma trận → kịch bản đã định: hoàn thành **F1+F2 offline + judge cho tập nhỏ**; mọi bảng ghi ngày chạy + `model_served`; phần không chạy được ghi "không chạy được vì hạ tầng", không nội suy.
6. **Quy tắc bảng kết quả (bắt buộc — vá review):** **mọi bảng số** phải kèm **`ngày chạy` + `model_served` + `hash manifest`**; thiếu 1 trong 3 ⇒ bảng không hợp lệ để trích vào báo cáo. **Canary 20 ca/ngày là tín hiệu, KHÔNG phải bảo đảm**: mẫu nhỏ (20 ca), ngưỡng Δ>5pp là thô, model free có thể đổi hành vi **giữa hai lần canary** ⇒ mọi so sánh dùng baseline **cùng ngày**, và mọi kết luận phải chịu được giả định "model đã đổi sau lưng router".

### 6.2 Số lần chạy + CI

- **≥5 vòng/cấu hình** ở ô chủ chốt ngoài chương trình lặp N=20 (K1/K2 có N=20/cell là chính); ô phụ 3 vòng. Mọi bảng chính: **mean ± SD** + Wilson CI 95%.
- **TPR@FPR**: bootstrap **stratified 1.000 resample** cho TPR@1%FPR + CI 95% mọi tỉ lệ khác.
- **Quy tắc tuyên bố:** chỉ nói "khác biệt" khi **CI không chồng lấp HOẶC Δ > MDD của ô đó**; các so sánh then chốt = C0 vs C3 vs C4 trên K1/K2 (pre-register — chống multiple comparisons/cherry-picking); các so sánh ngoài danh sách = exploratory, ghi rõ.
- **Kiểm soát đa so sánh (multiplicity — chốt):** **primary = 4 phép so sánh pre-registered** (C0-vs-C3 và C0-vs-C4, trên K1 và K2) — hiệu chỉnh **Holm–Bonferroni** trên họ primary (α = 0,05; báo cả p thô + p hiệu chỉnh + CI). **Exploratory** = mọi so sánh còn lại (các arm khác, ô khác, chỉ số phụ; gồm cả ΔVI–EN của RQ2 và recall theo lớp của RQ4) — **chỉ báo cáo kèm CI**, không dùng từ "có ý nghĩa thống kê", không đưa vào kết luận. Mỗi bảng ghi rõ thuộc họ nào.
- **Power (chốt):** n=100 ⇒ MDD ≈ **18,2 điểm %** (2609.25173); ⇒ ô quyết định **N=20 lần/cell** (§5.3); ô thiếu power (K2-VI, K4, K2-AD) **liệt kê trước** là "chỉ báo cáo".
- **Câu chốt hiệu ứng nhỏ (vá lượt 3):** **KHÔNG tuyên bố hiệu ứng dưới ~10 điểm %** (MDD ≈ **18,2 pp @ n=100** — §5.3); mọi Δ nhỏ hơn **chỉ báo cáo kèm CI** và ghi rõ là **chưa kết luận được**.
- **Ngưỡng dừng FPR hệ (giả thuyết ≤5% — vá lượt 3):** ≤5% là **giả thuyết, không phải kết quả** (§0.4 #2); ngưỡng dừng kèm theo: nếu **FPR hệ >10% trên tập benign ở M3** ⇒ **hạ F2 khỏi vòng can thiệp** (chỉ log) và ghi quyết định này vào manifest.

### 6.3 Over-defense (làm được ngay)

NotInject-style + mở rộng VI ("hướng dẫn", "bỏ qua", "chỉ dẫn", email hợp lệ, số 9–12 chữ số vô hại, emoji ZWJ, JWT/hash); **so ở cùng catch rate** (95%), không so ở ngưỡng mặc định; chạy lại T1–T4 dưới biến thể obfuscation; chia tập in-distribution vs "thực tế" mô phỏng LODO (vì CV-AUC vs LODO-AUC lệch **8,0–16,5 pp**).

### 6.5 Đối chứng độc lập (chống "tự chấm bài mình" — vá Q5/W2)

- **Tối thiểu 3 nguồn đối chứng:** (a) công cụ tấn công ngoài **garak 0.17.1 + PyRIT 1.1.0** (đã cài + CLI chạy thật — `attack-tooling-install-check.md`) chạy qua proxy; (b) **dữ liệu người-thật**: llmail `labelled_unique_*` (160.741+37.303), TensorTrust (69.906 unique), hackaprompt (600K) — đo trên bộ người-thật, không chỉ K1/K3/K4 tự sinh; (c) bộ recall-fill của F1 (T1–T5) trong đó T2/T4 có kiểm mẫu "còn đọc được".

### 6.6 Pre-registration — chốt TRƯỚC khi chạy arm (vá lượt 3)

Ghi thành văn bản khoá (`experiments/manifests/preregistration.md` + hash vào mọi run) **trước khi chạy arm đầu tiên**; mọi thay đổi sau đó **phải ghi vào nhật ký sai lệch** (deviation log: nội dung, lý do, ngày — không sửa âm thầm):

1. **Endpoint chính (primary):** ΔASR **C0-vs-C3** và **C0-vs-C4**, trên **K1 và K2** (= 4 phép so sánh primary, Holm–Bonferroni — §6.2).
2. **Ngưỡng tối thiểu được tuyên bố:** **~10 điểm %** — dưới ngưỡng chỉ báo cáo kèm CI, ghi "chưa kết luận được" (§6.2).
3. **Số lần chạy:** ô quyết định **N=20 lần/cell** (hạ cấp N=10→N=5 phải kê khai — §5.3); ô phụ ≥3 vòng.
4. **Gate judge:** ≥**150 mẫu gán tay** + **2 judge độc lập** (κ, flip rate, `ASR_corrected`) — điều kiện để tin mọi số ASR/leak (§6.4).
5. **Luật dừng kèm theo:** ngưỡng dừng FPR hệ (§0.4#2, §6.2).

### 10.3 Schema log JSONL (1 dòng = 1 record; hash-chain)

`run_id · ts_utc · schema_ver · record_id · prev_hash · record_hash` — rồi:
`session_id · session_family · subject_key · station(input|context|output) · direction(in|out) · arm(C0–C5) · cell(K1–K6) · lang(en|vi) · case_id · turn_idx · dataset{source_id, revision|hash} · model_requested · model_served · temperature · seed · max_tokens · stream_mode · request_shape_flags[] · views_used[] · decoded_layers · transforms[]({step:"B3", removed:3, cps:[…]}, {step:"B10", kind:"base64", bytes:64, preview_sha256}) · findings[]({detector_id, family, kind, label, span[start,end], score, severity, evidence_preview, span_hash_hmac, latency_ms}) · verdict{severity, quorum_families[], rule_id, thresholds_version} · action_taken(allow|block|mask|escalate|log) · config_hash · fail_mode_used · breaker_state · upstream_latency_ms · detector_latency_ms{} · total_latency_ms · ttft_ms · exposure_chars · tokens{prompt, completion} · retry_count · http_status · error_code_class(violation|guard_unavailable|none) · judge{model, prompt_hash, label, score, mode} · escalate_id · purpose(security) · retention_days · raw_sha256 · raw_len · masked:true`

**Bất biến:** `span` luôn quy về **text gốc** (raw) nhờ `offset_map`; mặc định **không** có text raw trong bất kỳ field nào (chỉ store điều tra riêng — §4.5); mọi record verify được bằng hash-chain.

### 10.4 Thuật ngữ

| Thuật ngữ | Nghĩa trong plan |
| --- | --- |
| **Proxy / trạm** | Điểm chặn OpenAI-compatible; 3 trạm = input / context / output |

| **Hot path / async** | Đường phản hồi đồng bộ (F1/F2 theo lịch) vs F3 chạy nền, áp verdict cho lượt sau |
